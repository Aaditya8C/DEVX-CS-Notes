# Redis
## Definition

Redis is an **in-memory data structure store** used as a cache, session store, message broker, real-time leaderboard engine, and queue. Single-threaded, persistence-optional, with atomic operations and publish-subscribe support.

---

## Core Data Structures

| Structure | Use Case | Operation Time |
|-----------|----------|-----------------|
| String | Cache values, counters, sessions | O(1) |
| List | Task queues, activity feeds | O(1) append/pop |
| Set | Unique items, tag indexing | O(1) add/remove |
| Sorted Set | Leaderboards, time-series scoring | O(log N) |
| Hash | Object storage, HGETALL patterns | O(1) per field |
| Bitmap | Binary flags, seen user tracking | O(1) bit ops |
| HyperLogLog | Approximate cardinality counting | O(1) space |
| Stream | Event logs, pub-sub with history | O(1) append |

---

## Single-Threaded Execution Model

All commands execute sequentially. **No locks needed** within a command boundary.

### Consequence
- **Blocking commands** (`BLPOP`, `BRPOP`, `BRPOPLPUSH`) halt the entire server.
- Long operations (Lua scripts, mass SCAN) impact latency for all clients.
- Cluster deployments provide horizontal scaling, not true concurrency.

**Best Practice:** Keep operations sub-millisecond; use pipelining to batch requests.

---

## Persistence

### RDB (Snapshots)
- Full state saved to disk at intervals or on explicit `SAVE`/`BGSAVE`.
- **Trade-off:** Fast recovery, risk of data loss between snapshots.

### AOF (Append-Only File)
- Every write appended to disk before ACK.
- **Higher durability, lower throughput.**
- Rewriting compacts the log periodically.

### Selection
- **Cache only**: No persistence (RDB/AOF disabled).
- **Durable session store**: AOF or hybrid.
- **Balanced**: RDB for speed, async AOF.

---

## High-Availability & Replication

### Master-Slave Replication
- Master accepts writes; slaves replicate asynchronously.
- **Failover manual** or automated via Sentinel.
- Slaves can serve reads (staleness possible).

### Sentinel
- Monitors master health; auto-promotes healthy slave on master failure.
- Configures clients to new master endpoint.
- **Requires ≥ 3 Sentinel nodes** for quorum.

### Cluster Mode
- Horizontal sharding via consistent hashing (16384 slots).
- Multi-master; each shard stores a subset of slots.
- Automatic failover via cluster elections.
- **Trade-off:** Cluster commands and cross-slot operations restricted.

## Memory Management

### Eviction Policies
When max memory is reached:

| Policy | Behavior |
|--------|----------|
| `noeviction` | Reject writes; reads continue |
| `lru` | Remove least recently used key |
| `lfu` | Remove least frequently used key |
| `ttl` | Remove soonest-expiring key |
| `random` | Random eviction |

**Decision:** Cache-only uses `allkeys-lru`. Session store uses `noeviction` + monitoring.

### Lazy Expiration
Keys expire on access, not background cleanup. High TTL with infrequent access can bloat memory.

---

## Common Patterns

### Cache-Aside
```
1. Check cache
2. If miss, load from DB
3. Write to cache with TTL
```

Simpler but risks **cache stampede** on thundering herd.

### Write-Through
```
1. Write to cache
2. Write to DB
3. ACK to client
```

Synchronous, slower, guarantees consistency.

### Write-Behind (Write-Back)
```
1. Write to cache
2. ACK to client (async DB write)
3. Batch/periodic flush to DB
```

Fast but risky on cache failure (data loss).

## Production Considerations

### Monitoring
- Memory usage, eviction rate, hit/miss ratio.
- Slow log (commands > threshold latency).
- Replication lag on replicas.
- Cluster migration/rebalancing load.

### Key Vulnerabilities
- **No built-in authentication** (pre-6.0); rely on network isolation.
- **FLUSHDB/FLUSHALL** dangerous; ACLS restrict dangerous commands (6.0+).
- **Pub-sub is fire-and-forget;** messages lost if subscriber offline.
- **Large pipelines** can cause client disconnects; batch size matters.

### Sizing
- **Peak QPS × 100-200 µs** ≈ steady-state throughput.
- 1 GB heap ≈ 10-50K concurrent connections (depends on key size).
- Cluster shards recommended when single shard hits 100K QPS or > 50% memory.

### Deployment Trade-offs

| Mode | HA | Sharding | Failover Speed | Complexity |
|------|-----|----------|---------|-----------|
| Standalone | None | No | Manual | Low |
| Sentinel | Yes | No | Seconds | Medium |
| Cluster | Yes | Yes | Seconds | High |
| Cloud (ElastiCache, Memorystore) | Yes | Yes | Managed | Low |

---

## Common Failure Modes

1. **Memory saturation**: Eviction thrashing, then client timeouts.
2. **Replication lag**: Stale reads or data loss if slave promoted without sync.
3. **PubSub subscriber offline**: Messages permanently lost (use Streams for durability).
4. **Network partition**: In cluster, minority partition goes read-only; singleton master becomes inaccessible.
5. **Persistence sync on startup**: Long recovery if AOF corruption or huge RDB.
