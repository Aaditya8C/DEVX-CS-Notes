# Cache Stampede

## Definition

Cache stampede (also **thundering herd**, **dogpiling**) occurs when **a popular cache key expires** and **hundreds or thousands of concurrent requests hit the database simultaneously** because they all miss the cache and fetch the same data.

Result: Database overload, latency spikes, and potential cascading failures.

---

## Why It Happens

```
Time T:
  Cache hit for key "user:100" (10K req/sec, response time 5ms)

Time T + TTL_EXPIRED:
  Key expires
  Concurrent requests arrive - all miss cache
  All 10K reqs hit database in same second
  Database connection pool exhausted
  Subsequent requests timeout or fail
```

**Severity factors:**
- Key popularity (QPS × TTL).
- Expiration pattern (synchronized expiry across similar keys).
- Database query cost.

---

## Root Causes

1. **Fixed TTL on popular keys** — Predictable expiration time creates synchronized overload.
2. **No refresh logic** — Cache waits for next request after expiration.
3. **Long generation time** — Expensive query amplifies impact when multiple requests compete.
4. **Thundering herd at scale** — 100K concurrent users hitting same key simultaneously.

---

## Mitigation Strategies

### 1. **Probabilistic Early Expiration (Xfetch)**
When expiration is near (e.g., 80% of TTL), a background process refreshes the cache **before expiration**.

```
Set TTL = 1000s
At 800s: Background refresh starts async
At 1000s: New cache value already set
```

**Trade-off:** Slightly stale data possible during refresh window; avoids stampede entirely.

**Cost:** Extra DB load for proactive refresh (but distributed over time).

---

### 2. **Locking (Mutex)**
One request "wins" and generates cache value; others wait for lock release and read the new value.

```
Request 1: Cache miss, acquires lock, fetches from DB, writes cache
Request 2: Cache miss, lock taken, waits
Request 3: Cache miss, lock taken, waits
Results 2&3: Lock released, reads refreshed cache
```

**Problem:** If lock holder crashes/times out, requests block indefinitely.

**Mitigation:** Lock timeout + fallback to direct DB query.

---

### 3. **Stale-While-Revalidate**
Serve stale cache value immediately while background fetch updates the cache.

```
Request arrives at T+1100s (expired at T+1000s):
  Cache returns stale value (age = 100s)
  Background task refreshes data asynchronously
  Next request gets fresh value
```

**Advantage:** Latency-neutral for client; DB query happens async.

**Trade-off:** Clients see slightly stale data briefly.

---

### 4. **Randomized TTL**
Add jitter to expiration times so keys don't expire simultaneously.

```
Base TTL: 1000s
Actual TTL: 1000 + random(0, 200) seconds
```

Reduces synchronized expiry but doesn't eliminate stampede if key is very popular.

**Limitation:** Only works when multiple similar keys exist.

---

### 5. **Cache Warming**
Preload cache during off-peak hours or service startup before user traffic arrives.

```
App startup:
  Load popular keys from DB into Cache
  TTL fresh; no expiration thundering
```

**Trade-off:** Requires knowing access patterns in advance; stale on next expiration.

---

### 6. **Separate Metadata Cache**
Store cache version/checksum separately; refresh only when version changes.

```
Cache: user:100 contains {version: V3, data: {...}}
Metadata: user:100:version contains V3

Expiration triggered on metadata key only
Full data cache stays until version changes
```

---

## Production Pattern: Layered Approach

Combine strategies for robustness:

```
1. Probabilistic early refresh (xfetch) — Primary defense
   ↓
2. Stale-while-revalidate fallback — Graceful degradation
   ↓
3. Randomized TTL jitter — Reduce synchronized peaks
   ↓
4. Database rate limiting — Prevent cascade if stampede occurs
   ↓
5. Alert on high cache miss rate — Alarm bell for stampede starting
```

---

## Detection

Monitor these signals:

| Signal | Indicates |
|--------|-----------|
| Spike in cache miss rate | Possible expiration event |
| Sudden DB connection pool saturation | Load from expired key |
| P99 latency spike | Concurrent DB queuing |
| Redis throughput drop (if forwarding cache gets) | Lock contention or stale invalidation |

---

## Common Scenarios

### 1. Leaderboard Expiration
Popular user's score cached with 5-minute TTL:
- 10K reqs/min baseline for this key
- At expiration, all 10K requests hit DB in seconds
- **Mitigation:** Probabilistic refresh + stale-while-revalidate.

### 2. Featured Content (Homepage)
Featured article cached for 1 hour:
- 100K hits/hour to same key
- Single expiry causes load spike
- **Mitigation:** Randomized TTL (±10 min) + cache warming.

### 3. Session Cache Synchronized Expiry
1M sessions all TTL'd at same time (midnight UTC, rotation, etc.):
- Predictable overload window
- **Mitigation:** Randomized session TTL jitter.
