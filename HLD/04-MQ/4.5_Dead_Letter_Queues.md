# Dead Letter Queues

## Definition

A **Dead Letter Queue (DLQ)** is a separate queue where messages that **fail to process successfully** after exhausting retries are sent for later inspection, debugging, or manual intervention.

Alternative names: **Poison queue**, **Error queue**, **Undeliverable queue**.

---

## Why DLQs Matter

```
Main Queue (process message):
  Success: Ack and remove from queue
  Transient Failure: Retry with backoff
  Permanent Failure (after max retries): DLQ
  Poison Message (corrupted, invalid): DLQ
```

Without DLQs:
- Messages loop forever, blocking queue processing.
- Consumer crashes or gets stuck in infinite retry loops.
- Legitimate messages behind blocked message never process.

---

## When Messages Go to DLQ

### 1. **Max Retries Exceeded**
```
Message fails processing 5 times
  Leads to DLQ (stop spinning on it)
```

### 2. **Permanent Error**
```
Message references non-existent resource
  Example: DELETE order from deleted customer ID
  Cannot recover with retries - DLQ immediately
```

### 3. **Consumer Crash**
```
Consumer processing message crashes/dies
  Message redelivered to another consumer
  Happens N times - DLQ to prevent infinite reprocessing
```

### 4. **Message Expiration**
```
Message in queue for > TTL
  Leads to DLQ (stale; likely won't process correctly now)
```

### 5. **Deserialization / Codec Failure**
```
Message format corrupted/invalid
  Leads to DLQ (will always fail deserialization)
```

## DLQ Configuration

### Queue Settings

| Parameter | Typical Value | Notes |
|-----------|-------|-------|
| `maxReceiveCount` | 3 | Attempts before DLQ; Kafka: custom retries + offset tracking |
| `messageRetentionTime` | 7-14 days | Keep DLQ msgs for debugging |
| `visibilityTimeout` | 30s | Consumer lock duration; SQS-specific |
| `delaySeconds` | 0s | No delayed delivery to DLQ |

### Retry Policy
```
Attempt 1: Immediate (catches quick recoveries)
Attempt 2: Exponential backoff 2s
Attempt 3: Exponential backoff 4s
Attempt 4: Exponential backoff 8s
After 4 failures: DLQ
```

## Monitoring & Alerting

### Metrics to Track

| Metric | Alert Threshold | Implication |
|--------|------|---|
| DLQ message rate | > 1/min | Messages failing persistently |
| DLQ queue depth | > 100 | Backlog of failed msgs |
| DLQ age (oldest msg) | > 1 day | Unhandled issues for extended period |
| Time-to-DLQ (latency) | > 5 min | Retries taking too long |

### Alert Conditions
- Any message in DLQ: investigate same day.
- DLQ rate spike: possible data schema change or service bug.
- Old messages in DLQ: someone forgot to process failures.

## Scenarios

### 1. Payment Processing
```
Message: Process refund for order #123
Problem: Order doesn't exist (already deleted)

Processing:
  Attempt 1: "Order not found" → Likely permanent
  Attempt 2-3: Exponential backoff (still not found)
  → DLQ after 3 attempts

Resolution:
  Oncall checks: Order was cancelled yesterday
  DLQ message is artifact of race condition; safely ignored
```

### 2. User Event Pipeline
```
Message: Track user activity event
Problem: Malformed JSON payload

Processing:
  Attempt all retries: Deserialization always fails
  → DLQ immediately (or after 1-2 attempts)

Resolution:
  Fix upstream event producer schema
  Manually replay DLQ after fix deployed
```

### 3. Email Notification Service
```
Message: Send email to user@example.com
Problem: SMTP server temporarily down

Processing:
  Attempt 1: Connection timeout → Retry
  Attempt 2: Connection timeout → Retry
  Attempt 3: Success!
  Message processed; stays in main queue AQ

If SMTP down for hours:
  Attempt 1-5: All fail
  → DLQ after max retries

Resolution:
  SMTP restored
  DLQ processed in batch once SMTP healthy again
```

## Architecture Pattern

```
                   Main Queue
                       ↓
              Message Consumer
                   /    |    \
           Success  Retry  Fail (permanent)
             /        |          \
       Processed   Backoff      DLQ Queue
                   Delay        /    |
                     |      Inspect  ?
                 Retry         |     |
                  Again    Manual   Auto
                             Replay Replay/Ignore
```

---

## Production Checklist

- DLQ configured on all message queues
- Max retries tuned per message type (3-5 typical)
- DLQ alerting configured (msg rate, queue depth)
- DLQ retention ≥ 7 days for debugging
- Admin tool to inspect/replay DLQ messages
- Oncall runbook for common DLQ patterns
- Monitoring dashboard showing DLQ health
- Metrics for DLQ processing latency & success rate
