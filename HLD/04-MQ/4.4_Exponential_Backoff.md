# Exponential Backoff

## Definition

Exponential backoff is a **retry strategy** where a failed request is retried with **increasing delay** between attempts. Delay grows as $2^{attempt}$ (or similar exponential function), with optional jitter.

Core idea: **Reduce load on a struggling service** by giving it time to recover between retry attempts.

---

## Basic Formula

$$\text{delay}_n = \text{base} \times 2^n + \text{jitter}$$

Where:
- $n$ = retry attempt number (0, 1, 2, ...)
- $\text{base}$ = initial delay (e.g., 100 ms)
- $\text{jitter}$ = random noise ∈ [0, max_jitter]

---

## Why Exponential (Not Linear)?

| Strategy | Backoff Pattern | Risk |
|----------|-----------------|------|
| **No backoff** | Immediate retry | Hammers struggling service; cascades |
| **Linear** | 1s, 2s, 3s, 4s | Still too aggressive for slow recovery |
| **Exponential** | 1s, 2s, 4s, 8s, 16s | Matches typical recovery curves |

**Exponential matches production recovery:** Services under load recover non-linearly. Early retries are too aggressive; longer waits let in-flight requests drain and queues clear.

---

## Jitter

Pure exponential backoff creates **synchronized retry thundering**:

```
Time 0: 1000 requests fail - all retry at T+1s
Time 1: All 1000 retry simultaneously - service overload again
```

**Solution: Add jitter (randomness)**

$$\text{delay}_n = \text{base} \times 2^n + \text{random}(0, \text{jitter}_{\max})$$

Spreads retries across time; prevents synchronized overload.

### Jitter Strategies

1. **Full Jitter**
   $$\text{delay} = \text{random}(0, \text{base} \times 2^n)$$
   Most variance; retries spread wide.

2. **Equal Jitter**
   $$\text{delay} = \frac{\text{base} \times 2^n}{2} + \text{random}(0, \frac{\text{base} \times 2^n}{2})$$
   Smaller variance than full; predictable bounds.

3. **Decorrelated Jitter**
   $$\text{delay}_n = \text{random}(0, 3 \times \text{delay}_{n-1})$$
   AWS recommendation; depends on previous delay.

---

## Max Retries & Caps

Exponential grows fast. Without bounds:

```
Attempt 0: 100 ms
Attempt 1: 200 ms
Attempt 2: 400 ms
Attempt 5: 3.2 seconds
Attempt 10: 102 seconds
```

**Best practice:** Set max_delay cap (e.g., 60s) to prevent waiting indefinitely.

$$\text{delay}_n = \min(\text{base} \times 2^n + \text{jitter}, \text{cap})$$

---

## Retry Policies (What to Retry?) 

**Idempotent operations only:**

| Error | Retry? | Reason |
|-------|--------|--------|
| `500 Internal Server Error` | Yes | Transient; server might recover |
| `503 Service Unavailable` | Yes | Explicit signal to backoff & retry |
| `429 Too Many Requests` | Yes | Rate limit; wait before retry |
| `400 Bad Request` | No | Client error; retrying won't help |
| `401 Unauthorized` | No | Auth issue; retrying won't fix it |
| `404 Not Found` | No | Resource doesn't exist |
| Network timeout | Yes | Transient network issue |
| Connection refused | Yes | Service might be restarting |

**Non-idempotent operations** (POST money transfers):
- Retry only if safe (e.g., purchase requests with deduplication tokens).
- Avoid blind retries on state-changing ops.

---

## Configuration Example

```
base_delay = 100 ms
max_delay = 30 seconds
max_attempts = 5
jitter_max = 100 ms

Attempt 0: delay = min(100 * 2^0 + random(0,100), 30000) = 100-200 ms
Attempt 1: delay = min(100 * 2^1 + random(0,100), 30000) = 200-300 ms
Attempt 2: delay = min(100 * 2^2 + random(0,100), 30000) = 400-500 ms
Attempt 3: delay = min(100 * 2^3 + random(0,100), 30000) = 800-900 ms
Attempt 4: delay = min(100 * 2^4 + random(0,100), 30000) = 1600-1700 ms
Total timeout budget: ~3.5 seconds
```

## Production Scenarios

### 1. Database Connection Retry
- Database service restarts (scheduled maintenance, crash, failover).
- Exponential backoff gives cluster time to elect new primary.
- First retry at 100ms catches fast failover; later retries catch slower scenarios.

### 2. API Rate Limiting (429)
- Client hits rate limit; backoff prevents thundering herd on rate-limit window reset.
- Jitter ensures staggered retry after window passes.

### 3. Message Queue Consumer
- Queue service briefly unavailable (rebalancing, restart).
- Exponential backoff reduces queue consumer CPU spinning; allows service recovery.

### 4. Cascading Failures
- Service A fails, leading to failure in Service B, leading to failure in Service C.
- Without backoff: Synchronous cascading request storms.
- With backoff: Retry delays decouple services; failures contained.

---

## Anti-Patterns

1. **Exponential backoff on obviously permanent errors** (400, 401, 404).
   - Wastes time waiting for something that won't change.
   - Fail fast instead.

2. **No jitter**: Results in synchronized thundering herd despite backoff.

3. **Too short max_delay cap**: Doesn't give service enough recovery time.

4. **Retrying non-idempotent operations** without deduplication.
   - Double-charging, duplicate orders, etc.
